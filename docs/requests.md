# 请求时间和线程回收

`PHP_TIMEOUT` 和 `MAX_REQUESTS` 已经有了。这一份把迁移时要守住的语义写清楚，并补上多条线程不要在同一时刻一起回收。

| 变量 | 默认 | 迁移时的常见值 |
|---|---|---|
| `PHP_TIMEOUT` | `60` | `120`，对齐原来 php-fpm 的 `request_terminate_timeout` |
| `MAX_REQUESTS` | `1000` | `650`，对齐原来的 `pm.max_requests`。`0` 表示不回收 |

值写在进程环境里。BaseHub 没有单独的字段，后台把它们放进这个进程的环境。前台、后台可以不同。跑 `crond` 或一次性 CLI 的进程不要设 `PHPHUB_MODE`，这两个变量对不接 HTTP 的命令也没有意义。

`PHP_TIMEOUT` 在 worker、index、file 三种模式里都生效。`MAX_REQUESTS` 只在 worker 循环里回收线程。index 和 file 会读到这个值，每个请求单独跑完，计数在下一次请求前清掉，不按它重启。

## 超时

时钟从请求到达算起，包括在队列里等待的时间。到点之后：

- 客户端还连着就得到 504。已经开始写正文时，连接直接关掉，不再补一页 HTML。
- 只回收正在跑这个请求的那条线程。其它线程继续 200。
- 不抓 PHP 调用栈，不在请求中途打断去采样。慢日志仍然只在请求正常结束时比较耗时。超时记在错误日志里，一行，带上方法、路径、脚本和耗时。
- 队列里还没分到线程就超时的请求也是 504，并且不占用一条 PHP 线程。

停容器时，等在途请求的上限仍是 `PHP_TIMEOUT`。不要为了迁移把这个等待再加一倍。

`PHP_TIMEOUT` 小于 1 秒，进程拒绝启动。

## 回收

回收只发生在 worker 循环里：一条线程处理完当前请求、调用过 `phphub_finish_request()` 之后，才比较自己的计数。打满之后只重启这条线程上的 PHP。进程不退出，其它线程不重启。

`PHPHUB_MODE` 为 `index` 或 `file`，以及自动判断成按次跑的脚本，不进入这个循环。设了 `MAX_REQUESTS` 也不会增加 `phphub_worker_restarts`。

线程是一起启动的。如果每条都用同一个 `MAX_REQUESTS`，它们会在同一批请求里一起重启，前面的请求全部排进剩下的线程。所以线程 `i` 的实际上限是 `MAX_REQUESTS + i`。`i` 从 0 开始，不超过线程数。18 条线程最多错开 17 个请求。`MAX_REQUESTS` 为 0 时都不回收。

回收记在 `phphub_worker_restarts`。错误日志一行，带上脚本和这条线程已经处理的请求数。不要在回收时清空 opcache，也不要重新读 php.ini。新线程用进程里已经加载的解释器状态。

## 性能

超时判断是请求循环里已经有的截止时间，不额外起一个定时器去轮询 PHP。队列里的超时发生在分发之前。

回收只发生在请求边界，发生在 `phphub_finish_request()` 之后。不在脚本执行中途拆解释器。

错开用的是线程编号，不算随机数，也不读时钟。

`SLOWLOG` 仍默认关。打开时每个请求只在结束时做一次比较。超时路径不写慢日志。

## 稳定性

一条线程超时或回收时，它持有的请求内状态随线程一起丢掉。worker 循环外面的应用对象属于进程，不因为一条线程回收而重建。下一条分到新线程的请求要重新进入 `phphub_handle_request()`。

扩展段错误仍然会让整个进程退出，由 Docker 拉起。超时和 `MAX_REQUESTS` 不能升级成进程退出。

上传进行中超时，临时文件按现有的请求结束路径删除，不留在 `/tmp`。

## 镜像里要有的东西

迁应用之前核对发布镜像，而不是在运行时现装：

- PHP 8.5 和 Phalcon 5.23 的 ZTS 构建。
- 应用要的扩展已经在镜像里：redis、memcached、beanstalk 客户端、mysqli。缺一个就在构建镜像时补，不进容器再 `docker exec` 编译。
- `crond` 在镜像里，Cron 进程的命令就是 `crond` 的前台形式，不设 `PHPHUB_MODE`。
- 应用放在 `/opt/bin` 的工具能在这个镜像里执行。不能执行就改镜像，不把宿主机的目录挂进来凑合。

这些是发布镜像的检查，不是这条进程的请求路径。请求路径上不要为了核对去 `stat` 这些二进制。
